OpenClaw Bot → Deposit CRM API

Everything the bank-scraping bot needs to push detected deposits into the CRM and reconcile them against player records. These are the only endpoints the bot uses — the rest of the CRM sits behind human login and isn't your concern.

Transactions + full CRUD Auth: API key Format: JSON Idempotent writes

Overview

What this API is for

The bot detects bank credit transactions and reports them here. The CRM then lets a Customer Service agent attach a bonus and a game, and auto-tops-up the player. Two integration styles are supported — see Integration patterns — and both use the same endpoints below.

You send us data; we never call back into your bot. Integration is pull/push over HTTPS only.

Base URL
https://seven11bo.online
!
The apex 308-redirects to www.seven11bo.online. curl follows that automatically, but many HTTP clients do not follow redirects on POST by default — and a dropped 308 looks like success while the request never arrives. Either enable redirect-following, or point $BASE straight at https://www.seven11bo.online.

Authentication

API key in a header

Every request carries the API key in the X-API-Key header. The key is issued once and stored hashed in the CRM — a missing or invalid key returns 401.

X-API-Key: dbk_••••••••••••••••••••••••••••••••
!
The live key is delivered separately over a secure channel, never in this document. Treat it as a secret — it grants full access to create and read transactions. If it leaks, tell the CRM team and we rotate it immediately.
Company-scoped keys

A key can be scoped to a single company. When it is, it's prefixed with that company's leader code (e.g. alpha_dbk_…) and its reads are limited to that company's data: GET /api/bot/bank-accounts returns only that company's accounts, and GET /api/bot/kiosks (and /:id) only that company's kiosks — an out-of-scope id returns 404. An unscoped key (dbk_…, no prefix) has full access. Scope is enforced server-side by the key; you don't pass a company id.

Optional IP allowlist

If the bot runs from a fixed egress IP, the key can be locked to that IP so a leaked key is still useless from anywhere else — requests from other IPs then return 403. This is opt-in; send the CRM team your IP to enable it. The API key stays the primary control; the allowlist is a second layer.

Endpoint

Get /api/bot/transactions List

Fetch transactions the CRM is waiting on. Deposits, withdrawals, bank transfers and game transfers are returned as one stream — every item carries a type field ("deposit", "withdrawal", "transfer", or "game_transfer"). For bank transfers only, the dedicated Transfers resource offers account_id/offset filters.

Manual items are never returned. Deposits, withdrawals and transfers created with "Handle manually (skip bot)" are excluded from every bot endpoint — a human approves/completes/confirms them in the CRM, so your bot never sees or acts on them.

i

Endpoint

Patch /api/bot/transactions/:id/status Complete

Drive a deposit through the top-up lifecycle. :id is the numeric id or your external_id.

The flow: a CS agent picks the game + bonus and clicks Approve in the web app → the deposit moves to processing (no money moves yet). Poll GET /api/bot/transactions?status=processing to find deposits waiting for top-up, do the real provider top-up, then PATCH …/status with completed (or failed). The row in the web app flips on its own — it auto-refreshes every 10s.

Where the money moves: the completed transition is the only one that books the deposit — the CRM credits the player's game balance (+total), deducts the company BO pool if one exists, and bumps total_deposits. failed moves no money, so there's nothing to reverse. Re-sending completed is a safe no-op — it never credits twice.

Body fields
FieldTypeDescription
statusstringRequired. One of approved, processing, completed, failed.
game_topup_referencestringProvider top-up receipt; stored on the record.
notestringFree text, kept in the audit log.
Allowed transitions (forward-only)
From→ to
pending / matchedapproved, processing, completed, failed
approvedprocessing, completed, failed
processingcompleted, failed
completed / failedterminal (no change)
Request
curl -X PATCH "$BASE/api/bot/transactions/42/status" \
  -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{ "status": "completed", "game_topup_reference": "PROV-99887" }'
Status codes
200Updated — returns the transaction. Re-sending the current status returns "unchanged": true.
409Illegal transition; body includes allowed_from_here.
422On completed: the company BO pool has insufficient credit for the game.
400Missing or invalid status.
404No transaction with that id.
i
Failed → reprocess. When you send failed, the web app shows the deposit as Failed with a Reprocess button for CS. Reprocess sends it back to pending so CS can adjust and re-approve — which re-dispatches it to you as processing. Nothing to call on your side; just keep polling processing. Since failure credits nothing, a reprocessed-then-completed deposit still credits exactly once.

Resource

Bank accounts

Collection and payout accounts owned by an entity. role: "deposit" = player collection (the accounts the bot watches); role: "withdrawal" = payouts. GET responses include the account's online-banking login — company_id, username, password, pin (also exposed as login_company_id / login_id / login_password / login_pin); these are null until an admin fills them in. A company-scoped key returns only its own company's accounts.

company_id — enterprise accounts (Maybank2u Biz, CIMB BizChannel and the like) ask for a company/organisation ID before the user ID. When it is set, enter it on the first login screen; when it is null the account is personal and there is no such field.

device_id — the device this account's banking app is bound to. Banks tie a login to one registered device, so when a balance stops updating the first question is which device was on it. Report it as you pick the account up; send null to clear it when the account moves off a device. It shows against the account on the CRM's Bot Health page and is searchable there, so "which account is on device X" is one query.

Withdrawals

Player cashouts. Lifecycle: requested → credits_pulled → paid (or failed). The two action endpoints move money and run in a single database transaction.

Listing and creating are merged into /api/bot/transactions: list with GET /api/bot/transactions?type=withdrawal, create with POST /api/bot/transactions and {"type":"withdrawal", …}. The old GET/POST /api/bot/withdrawals collection routes were removed. The lifecycle routes below (/:id/*) are unchanged.

withdraw_all — when a withdrawal carries "withdraw_all": true, empty the player's wallet for that game and report what you found: POST /api/bot/withdrawals/:id/pull with {"amount": <what you pulled>}. Such a request has requested_amount: 0 — the figure is not known when CS raises it, which is the whole point of the flag.

Our game_credits is a cache you refresh, so treat it as a hint, never a limit: a request may legitimately ask for more than the balance we hold, and your reported amount is always taken as the truth.

Resource

Game transfers

Move a player's credits between two of their games. Two flows:

  • CS-requested (bot-driven): a CS agent requests a transfer in the CRM. It's queued as pending and no credits move yet. You claim it, do the real game-provider back-office move, then drive it to completed (credits move then) or failed (nothing to reverse).
  • Bot-initiated: you did a move on your own — POST records it as already completed and moves the credits immediately.
pending ──you claim──▶ processing ──▶ completed
   ▲                       │       └─▶ failed
   └──── solving ◀─stalled─┘
!
This changed — one line to update in your bot. Transfers used to be created directly as processing. They are now queued as pending. Poll ?status=pending,solving — a bot still polling ?status=processing will see an empty queue forever.

Stalled transfers are re-queued automatically. A transfer we haven't heard back on for 5 minutes — whether you never claimed it, or claimed it and went quiet — is moved to solving with attempt_count bumped and its clock reset. solving is both what CS sees ("we're recovering this") and the re-queue: you pick those up exactly like pending ones. After 3 attempts it is failed automatically with a note.

solving means you have seen this transfer before. Check the provider back-office before moving credits again — otherwise a transfer that actually succeeded but failed to report back gets moved twice.

Get/api/bot/game-transfersList

Patch/api/bot/game-transfers/:id/statusClaim & complete

Drives a transfer through its lifecycle. Body: status (processing | completed | failed), optional note.

  • processing — claim it. You're starting the back-office move now. Valid from pending or solving. Claiming one you already hold is a no-op, not an error, so retrying after a timeout is safe. Claiming also restarts the 5-minute stall clock, so it measures from when you started rather than when CS asked.
  • completed — credits move from_game → to_game atomically. The source balance is re-validated under a row lock, so a stale balance yields 422 and nothing moves.
  • failed — nothing moves, nothing to reverse.

Claiming is optional — going straight from pending to completed still works. You only lose the "is anyone actually on this" signal.

# 1. claim it — you're starting now

  -H "Content-Type: application/json" \
  -d '{ "status": "processing" }'

  -H "Content-Type: application/json" \
  -d '{ "status": "failed", "note": "Mega888 BO rejected it: account locked" }'
i
Always send a note when you fail one. It's stored on the transfer and shown to CS as the reason. A failure without one just reads as "failed, no reason given" and someone has to come and ask you.

On-demand commands

Your second work queue, alongside game transfers. This one is CS pressing a button and waiting: "the player says they've paid — go and look now."

You already sweep the banks on your own cycle. Sometimes that cycle is too slow, so the Deposits page has a Crawl banks button that queues a command here. Poll it on your normal loop, claim what you take, report what you found.

pending ──you claim──▶ running ──▶ completed
                          └───────▶ failed
   (nobody claimed in time) ───────▶ expired
!
A command has a 10-minute shelf life. A crawl requested at 09:00 must not fire at 14:00 when you come back from an outage — by then the scheduled sweep has read those transactions and the CS who pressed the button has stopped waiting. Unclaimed commands past expires_at are swept to expired automatically, so you are never handed a stale one. A command you claim and go quiet on for 10 minutes is failed for you, with a reason.

Nothing on a command moves money. A failed or expired crawl costs nothing but the wait until your next scheduled sweep.

Get/api/bot/commandsPoll

Defaults to ?status=pending — what a polling agent wants. ?status= also takes a comma-separated list (pending, running, completed, failed, expired) or all; an unknown status is a 400 rather than a silently unfiltered list. ?command=crawl_bank narrows by kind, ?limit= caps the page (default 20, max 100). Oldest first — whoever has been waiting longest gets served first.

curl "$BASE/api/bot/commands?status=pending" -H "X-API-Key: $KEY"

# → 200 OK

  { "command_id": 7, "command": "crawl_bank", "status": "pending",
    "bank_account_id": null, "company_entity_id": 3,
    "requested_by_user_id": 5, "bot_id": null,
    "result": null, "error": null,
    "expires_at": "2026-08-21T03:46:24.282Z",
    "claimed_at": null, "completed_at": null,
    "created_at": "2026-08-21T03:36:24.282Z",
    "targets": [
      { "account_id": 1, "bank_name": "Maybank",
        "account_number": "512345678901",
        "account_holder": "MPG SDN BHD",
        "company_id": null, "username": "maybank_user",
        "password": "…", "pin": "…",
        "device_id": "SM-A155F" } ] } ] }

targets is the resolved list of accounts to read — the same shape /api/bot/bank-accounts returns, logins included, so there is no second call to make. It is resolved at read time, so an account added or deactivated since the button was pressed is handled correctly. bank_account_id set → just that account; null → every active deposit account in the command's company scope (a crawl is about money coming in, so payout accounts aren't in it).
Patch/api/bot/commands/:id/statusClaim & report

Body: status (running | completed | failed), optional bot_id, result, error.

  • running — claim it. Send bot_id so a command that then goes quiet points at the process to look at. Claiming one you already hold is a no-op, not an error.
  • completed — you did the work. Put the counters in result.
  • failed — say why in error. Nothing is reversed; the scheduled sweep covers the same ground shortly.

Claiming is optional — pending straight to completed works. You only lose the "someone is on this" signal CS sees while you work.

# 1. claim it — you're looking now
curl -X PATCH "$BASE/api/bot/commands/7/status" -H "X-API-Key: $KEY" \
  -H "Content-Type: application/json" \
  -d '{ "status": "running", "bot_id": "bank-crawler-1" }'

#    then close the command out with the counts
curl -X PATCH "$BASE/api/bot/commands/7/status" -H "X-API-Key: $KEY" \
  -H "Content-Type: application/json" \
  -d '{ "status": "completed", "bot_id": "bank-crawler-1",
       "result": { "accounts_crawled": 2, "transactions_found": 7, "deposits_created": 2 } }'

# ...or say why it didn't work
curl -X PATCH "$BASE/api/bot/commands/7/status" -H "X-API-Key: $KEY" \
  -H "Content-Type: application/json" \
  -d '{ "status": "failed", "error": "Maybank2u asked for a TAC" }'
i
Always send a result, even an empty one. It is free-form JSON; the CRM reads deposits_created and falls back to transactions_found for the line shown next to the button. Send { "deposits_created": 0 } rather than nothing when you found nothing — otherwise a crawl that found nothing and a crawl that reported nothing look identical to the person who pressed the button.

404No such command.
409Already completed, failed or expired — it can't be changed. Expired is a 409 on purpose: nobody is waiting for it any more, and reporting work against it would put a stale result in front of CS.

Reference

Two integration patterns

Both are supported — use whichever fits how the bot works. You can also mix them.

A Push

The bot detects a credit → POST /transactions → it appears in the CRM as pending → a CS agent approves. Simplest path; nothing else required from the bot.

B Intent + match

A CS agent pre-creates an intent when the player messages → bot polls GET ?status=pending_match → finds the matching bank credit → PATCH /match. Use when you want the CS-entered expectation reconciled against the bank.

Reference

Deposit status lifecycle

A transaction created via push starts at pending; one created as an intent starts at pending_match and joins the queue once matched. A CS agent then approves it.

pending_match — match → matched ┐
pending_match — match → pending → CS approves → completed
pending_match — match → pending └ or → failed
Game transfer status lifecycle

A CS-requested credit move. Queued as pending, claimed by you into processing, then driven to a terminal state. One we haven't heard back on for 5 minutes is re-queued as solving — see Game transfers.

pending ──you claim──▶ processing ──▶ completed
   ▲                       │       └─▶ failed
   └──── solving ◀─stalled─┘

pending shows in the CRM as Initializing. solving means we have already handed you this transfer once — check the provider back office before moving credits again.

Reference

Error responses

Every non-2xx response is JSON with a human-readable error. Codes used across the API:

400Bad request — a required field is missing or malformed.
401Unauthorized — missing or invalid X-API-Key.
403Forbidden — key is valid but the request IP isn't on its allowlist.
404Not found — no transaction or member for that identifier.
409Conflict — the transaction isn't in a state that allows this action.
422Unprocessable — e.g. a non-credit type or an amount that doesn't reconcile.
